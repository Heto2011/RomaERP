# RomaERP

نظام تخطيط موارد المؤسسات (ERP) — يغطي **المحاسبة المالية**، **الموارد البشرية**، و**المخزون**، مبني بـ Clean Architecture.

## التقنيات

- **Backend:** ASP.NET Core 8 Web API (C#), Clean Architecture (Domain / Application / Infrastructure / API)
- **Database:** SQL Server + Entity Framework Core
- **Auth:** ASP.NET Core Identity + JWT، مع صلاحيات حسب الدور (Admin / Accountant / HR / Employee)
- **Frontend:** React + TypeScript + Vite

## هيكل المشروع

```
src/
  RomaERP.Domain          # الكيانات والـ Enums (لا تعتمد على أي مكتبة خارجية)
  RomaERP.Application     # DTOs + منطق العمل (Services) + الـ Interfaces
  RomaERP.Infrastructure  # EF Core DbContext, Migrations, Identity, JWT
  RomaERP.API             # Controllers, Program.cs, Swagger
tests/
  RomaERP.UnitTests
frontend/                 # React + TypeScript
```

## الموديولات الحالية

### المحاسبة المالية
- شجرة حسابات كاملة (أصول / خصوم / حقوق ملكية / إيرادات / مصروفات) مبنية على أساس الاستحقاق المحاسبي، بما فيها حسابات **المصروفات/الإيرادات المقدمة والمستحقة**.
- سنوات وفترات محاسبية.
- قيود يومية بنظام القيد المزدوج (Double-Entry) مع التحقق من التوازن، والترحيل، وعكس القيود.
- ميزان المراجعة.
- **قائمة الدخل** و**قائمة المركز المالي** (مبنيتين مباشرة من القيود المرحّلة).
- **إقفال الفترات والسنوات المالية**: إقفال فترة يمنع الترحيل عليها، وإقفال السنة ينشئ قيد إقفال تلقائي يصفّر حسابات الإيرادات والمصروفات ويرحّل صافي الربح/الخسارة لحساب الأرباح المرحلة.
- **الأرصدة الافتتاحية**: شاشة مخصصة لإدخال ميزان المراجعة النهائي القادم من نظام العميل القديم عند بدء الاشتراك، بدل البدء من صفر — تتحقق من توازن الأرصدة وتمنع الإدخال المزدوج لنفس السنة المالية.
- **الأصول الثابتة والإهلاك**:
  - شجرة الحسابات فيها **حساب مجمع إهلاك منفصل لكل فئة أصل ثابت** (مباني / آلات ومعدات / أثاث وتجهيزات)، مش حساب واحد مجمّع للكل — كل أصل بيتقفل حسابه لوحده على المركز المالي.
  - تسجيل الأصل الثابت: تكلفة الشراء، تاريخ الشراء، العمر الإنتاجي بالسنين، قيمة الخردة (اختيارية)، وطريقة الإهلاك — **قسط ثابت** (نفس المبلغ كل شهر طول العمر الإنتاجي) أو **قسط متناقص** (نسبة % من القيمة الدفترية المتبقية، فبيقل المبلغ تدريجيًا كل شهر).
  - شاشة "قيود الإهلاك": بتحسب تلقائيًا قيمة إهلاك كل الأصول النشطة عن فترة محاسبية معينة (مسودة قابلة للمراجعة)، وبعد الترحيل بينشئ قيد محاسبي واحد (مدين مصروف الإهلاك `5400` / دائن حساب مجمع الإهلاك الخاص بكل فئة)، ويحدّث مجمع الإهلاك والقيمة الدفترية لكل أصل تلقائيًا. الإهلاك بيتوقف تلقائي لما يوصل الأصل لقيمة الخردة.

### الموارد البشرية
- الأقسام والوظائف والموظفون.
- عناصر الأجر (بدلات / استقطاعات) قابلة للربط بحسابات دليل الحسابات.
- دورات رواتب: إنشاء وحساب تلقائي → اعتماد → ترحيل، وينتج عنها قيد محاسبي تلقائي (مصروف مرتبات مقابل مرتبات مستحقة).

### المساعد الذكي للمصروفات (Claude AI)
- شاشة محادثة: الموظف يكتب المصروف بلغة طبيعية (مثال: "اشتريت بنزين بـ100 جنيه")، والمساعد (Claude API) بيستخرج المبلغ والوصف وأنسب حساب مصروفات من دليل الحسابات تلقائيًا.
- لو المبلغ مش واضح، المساعد بيسأل توضيح. بعد ما يتحدد المبلغ والبند، بيسأل على مرحلتين:
  1. **"عهدة ولا جاري (حساب الشركة)؟"** — عشان يعرف مصدر تمويل المصروف الأول.
  2. لو **جاري**: يسأل بعدها **"كاش ولا شبكة؟"**.
     - **كاش:** يروح مباشرة لشاشة "اعتماد المصروفات" في انتظار موافقة المدير.
     - **شبكة:** يفضل معلّق (مع إمكانية إرفاق صورة الإيصال كإثبات) لحد ما يتطابق تلقائيًا مع كشف حساب البنك، وبعدها يروح هو كمان لانتظار الاعتماد.
  3. لو **عهدة**: يسأل عن اسم/كود الموظف صاحب العهدة (بدون سؤال كاش/شبكة، لأنه مش مهم مع العهدة)، وبمجرد ما يتحدد الموظف يروح مباشرة لانتظار الاعتماد.
- **محاسبة العهد:** حساب واحد إجمالي في دليل الحسابات ("عهد الموظفين" — كود `1170`، أصول متداولة) مع رصيد فرعي لكل موظف (زي حسابات العملاء). عند الاعتماد يتسجل قيد **مدين مصروف / دائن عهد الموظفين**، وبينقص رصيد عهدة الموظف بقيمة المصروف تلقائيًا.
- **المطابقة البنكية:** رفع كشف حساب (CSV) أسبوعي/شهري، مطابقة تلقائية بالمبلغ والتاريخ (خلال ±5 أيام)، ومطابقة يدوية للحالات الغامضة.
- **الاعتماد إجباري دايمًا:** لا يوجد أي مصروف من المساعد الذكي (عهدة، كاش، أو شبكة) بيترحّل في الحسابات من غير موافقة صريحة من **Admin فقط** على شاشة "اعتماد المصروفات" — الاعتماد بينشئ القيد المحاسبي، والرفض بيلغي الحركة بدون ترحيل.
- **محتاج مفتاح Claude API** (راجع "تفعيل المساعد الذكي" تحت) — من غيره الشاشة بتشتغل وبترجع رسالة واضحة إنه لازم يتفعّل، من غير ما تعطل باقي النظام.

### المخزون
- أصناف وتصنيفات ومخازن.
- حركات استلام وصرف بنظام **المتوسط المرجح للتكلفة** (Weighted Average Cost)، مع منع صرف كمية أكبر من الرصيد المتاح.
- كل حركة بترحّل تلقائيًا للمحاسبة (استلام: مدين مخزون / دائن موردين — صرف: مدين تكلفة بضاعة مباعة / دائن مخزون)، مع إمكانية الربط بمركز تكلفة.

### المبيعات والمشتريات
- شاشتا عملاء وموردين (كود، اسم بالعربي/الإنجليزي، تليفون، بريد، رقم ضريبي)، كل واحد بيحتفظ برصيد آجل جاري (زي حساب العميل/المورد).
- **فاتورة المبيعات/المشتريات فيها اختيار طريقة السداد مباشرة** (أيقونة 💵 كاش / 💳 شبكة / 🗓 آجل) وقت إنشاء الفاتورة:
  - **كاش أو شبكة:** الفاتورة بتترحّل وتتحصّل/تتسدد فورًا (مدين الصندوق أو البنك مباشرة)، من غير ما تلمس رصيد العميل/المورد.
  - **آجل:** الفاتورة بتترحّل على حساب العملاء/الموردين (AR/AP)، ورصيد العميل أو المورد بيزيد بقيمتها، من غير ما يتحصّل/يتسدد حاجة وقتها.
- **أيقونة "💰 تسجيل تحصيل/سداد"** بتظهر بس على الفواتير الآجلة اللي لسه ليها رصيد متبقي — بتفتح نافذة تسجيل دفعة (المبلغ وطريقة الدفع: كاش أو شبكة)، وبتقلل الرصيد المتبقي ورصيد العميل/المورد تلقائيًا، وبيتقبل تحصيل/سداد جزئي على أكتر من مرة.
- **الضريبة تتحسب تلقائيًا** على كل فاتورة حسب نسبة `CompanySettings.VatRate` بتاعة الشركة (زي ما اتشرح في قسم "تعدد العملاء")، وبترحّل على حساب ضريبة مخرجات (`2161`) للمبيعات أو ضريبة مدخلات (`1180`) للمشتريات.
- **بند فاتورة المبيعات ممكن يتربط بصنف من المخزون (اختياري):** كل بند فيه قايمة "الصنف" — لو اخترت صنف، الوصف بيتملى تلقائي من اسم الصنف، والمخزن بيبقى إجباري في الفاتورة. لو سبته "بند خدمة" (بدون صنف) الفاتورة بتترحّل عادي من غير أي حركة مخزون — مفيد للخدمات أو أي بند مالوش صنف مخزّن.
  - عند الحفظ: بيتم التحقق إن الكمية المطلوبة متوفرة في المخزون قبل أي ترحيل (لو مش متوفرة، بترجع رسالة واضحة وميترحّلش حاجة).
  - بيتسجل صرف مخزون (Stock Movement) بنفس تكلفة المتوسط المرجح الحالية للصنف، ورصيد الصنف بينقص فورًا.
  - بيترحّل **قيد تكلفة بضاعة مباعة منفصل** (مدين `5500` تكلفة البضاعة المباعة / دائن `1160` المخزون) لكل بنود المخزون في الفاتورة مجمّعة، بالإضافة لقيد الإيراد العادي — يعني كل فاتورة فيها أصناف بتنتج قيدين محاسبيين مترابطين (الإيراد، والتكلفة).
- فواتير المشتريات لسه محتاجة اختيار حساب لكل بند بايدك (زي القيد اليدوي) بدل ربط تلقائي بالمخزون — استلام مخزون فعلي بيتم من شاشة "حركات المخزون" لوحده حاليًا.
- **شاشتا "أعمار ديون العملاء/الموردين"** (AR/AP Aging): تقرير لكل عميل/مورد ليه رصيد آجل لسه متحصّلش، مقسّم حسب عمر كل فاتورة (لغاية 30 يوم، 31-60، 61-90، أكتر من 90 يوم) اعتمادًا على تاريخ الفاتورة مقابل النهاردة — بيوضح مين متأخر في السداد وقد إيه.

### الفاتورة الإلكترونية (E-Invoicing) — مصر (ETA) والسعودية (ZATCA)

كل شركة (Tenant) تقدر تفعّل منظومة الفاتورة الإلكترونية المطابقة لدولتها من شاشة "الإدارة ← الفاتورة الإلكترونية" (Admin فقط):

- **مصر — منظومة الفاتورة الإلكترونية (ETA):** بناء مستند JSON بمواصفات الـ ETA (مُصدر/مُستلم، بنود، ضريبة T1)، مع تمييز تلقائي بين B2B (النوع "B") وB2C (النوع "P") حسب وجود الرقم الضريبي للعميل.
- **السعودية — فاتورة (ZATCA):** بناء مستند UBL 2.1 XML، مع:
  - **سلسلة تجزئة (Hash Chain):** كل فاتورة بتحمل رقم تسلسلي (ICV) وتجزئة الفاتورة اللي قبلها (PIH) بحيث تتربط الفواتير ببعض بشكل غير قابل للتلاعب — بيتم التحقق من كده تلقائيًا (فاتورة تانية بيتغيّر الـ ICV والـ PIH بتاعها).
  - **كود QR** بصيغة TLV (Tag-Length-Value) حسب مواصفات ZATCA.
  - **توجيه تلقائي حسب نوع الفاتورة:** فاتورة B2B (عميل له رقم ضريبي) تروح على **Clearance API**، وفاتورة B2C (بدون رقم ضريبي) تروح على **Reporting API**.
- **بيانات الاعتماد (Client ID / Secret / الشهادة / المفتاح الخاص) بتتخزن مشفّرة** في قاعدة بيانات كل شركة على حدة (باستخدام ASP.NET Data Protection)، ومفيش أي endpoint بيرجّعها في صورة نص واضح بعد الحفظ — شاشة الإعدادات بتوريك بس "محفوظة" أو "غير محفوظة"، ولو عايز تغيّرها تدخل قيمة جديدة وسيبها فاضية تفضل زي ما هي.
- من شاشة "فواتير المبيعات": كل فاتورة ليها حالة فاتورة إلكترونية (لم تُرسل / قيد الإرسال / مقبولة / مرفوضة) وزرار "إرسال للفاتورة الإلكترونية" يظهر لحد ما تتقبل.
- **مهم:** التوقيع والإرسال الفعلي للمنظومتين الحكوميتين مبني حاليًا على واجهات وهمية (Mock) — كل التصميم (بناء المستند، التوقيع، الإرسال) جاهز وقابل للاستبدال بتنفيذ حقيقي بمجرد توفر بيانات اعتماد عميل فعلي:
  - **ETA:** التوقيع الفعلي محتاج توكن USB فعلي (زي ePass2003) موصّل بجهاز عند العميل — مش ممكن يتم من السيرفر لوحده، فمحتاج "وكيل توقيع" محلي عند العميل.
  - **ZATCA:** محتاج شهادة CSID فعلية من رحلة التسجيل الرسمية (CSR ← Compliance CSID عن طريق OTP من fatoora.zatca.gov.sa ← اختبار 6 فواتير ← Production CSID).

### إدارة المستخدمين

شاشة "الإدارة ← المستخدمون" (Admin فقط، بتظهر في القائمة الجانبية لدور Admin بس) بتدير مستخدمي الشركة الحالية:
- عرض كل المستخدمين مع أدوارهم وحالتهم (نشط/متوقف).
- إنشاء مستخدم جديد (اسم، بريد، كلمة مرور، دور أو أكتر).
- تعديل أدوار أي مستخدم.
- إيقاف/تفعيل حساب مستخدم — الحساب الموقوف بيترفضله تسجيل الدخول فورًا.
- **حماية من قفل النظام على النفس:** الـ Admin مقدرش يوقف حسابه هو، ولا يشيل دور Admin عن نفسه.

العزل بين الشركات تلقائي بالكامل هنا زي أي جزء تاني في النظام — كل endpoint بيشتغل على قاعدة بيانات الشركة اللي جاية في هيدر `X-Company-Code`، فمفيش أي كود إضافي محتاج للعزل.

### "بياناتي" — صلاحية الموظف على بياناته هو بس

كل مستخدم (أي دور) عنده شاشة "بياناتي" في القائمة الجانبية (قسم "عام") بتعرض بياناته الوظيفية الشخصية (الاسم، القسم، الوظيفة، الراتب الأساسي، تاريخ التعيين) وسجل رواتبه (كشوف الرواتب المعتمدة أو المرحّلة فقط — مش المسودات) — من غير ما يقدر يشوف بيانات أي موظف تاني.
- الربط بين حساب الدخول والموظف بيتم من شاشة "الإدارة ← المستخدمون" (Admin فقط): كل مستخدم له قايمة "الموظف المرتبط" تختار منها أي موظف، وربط موظف بمستخدم جديد بيشيل الربط القديم تلقائيًا (علاقة واحد لواحد).
- المستخدم اللي لسه مالوش موظف مرتبط بيشوف رسالة واضحة في شاشة "بياناتي" بدل ما يقابل خطأ.
- دور Employee تحديدًا مقدرش يشوف قايمة كل الموظفين ولا كل دورات الرواتب (endpoints دي لسه Admin/HR/Accountant بس) — شاشة "بياناتي" هي الطريقة الوحيدة اللي بيشوف بيها بياناته.

## اللغة (عربي/إنجليزي)

الواجهة بتدعم التبديل بين العربي (RTL) والإنجليزي (LTR) من زرار في أعلى القائمة الجانبية (وفي شاشة الدخول)، واللغة المختارة بتتحفظ محليًا وتفضل زي ما هي في الزيارة الجاية. الاتجاه (RTL/LTR) بيتغير فعليًا في تخطيط الصفحة كلها مش بس النصوص. **كل شاشات النظام مترجمة بالكامل** (تسجيل الدخول، القائمة الجانبية، المبيعات والمشتريات، المحاسبة، الموارد البشرية، المخزون، المساعد الذكي، إدارة المستخدمين) باستخدام نظام ترجمة موحّد في `frontend/src/i18n/`. البيانات المدخلة من المستخدم نفسها (أسماء العملاء، أوصاف القيود، إلخ) بتفضل زي ما اتكتبت طبعًا ومبتتترجمش.

## الصلاحيات حسب الدور

| الدور | الوصول |
|---|---|
| Admin | كل شيء، بالإضافة لإقفال السنوات المالية وفتح الفترات |
| Accountant | المحاسبة الكاملة (حسابات، قيود، تقارير، إقفال فترات)، المخزون، المساعد الذكي والمطابقة البنكية، ومشاهدة/ترحيل الرواتب |
| HR | الموارد البشرية الكاملة (موظفين، رواتب، اعتماد دورات الرواتب) |
| Employee | وصول عام فقط (بيانات مرجعية مثل الفترات المالية)، بالإضافة لشاشة "بياناتي" (بياناته الوظيفية وسجل رواتبه هو بس، لو حسابه مرتبط بسجل موظف) — لا يشوف بيانات مالية أو رواتب أي حد تاني |

## التشغيل محليًا

### أسهل طريقة: أمر واحد عن طريق Docker

لو مش عايز تثبّت .NET وNode.js وSQL Server لوحدهم على جهازك، ده أسرع طريق:

1. ثبّت **Docker Desktop** (مجاني): [docker.com/products/docker-desktop](https://www.docker.com/products/docker-desktop/) — بعد التثبيت افتحه وسيبه شغال.
2. حمّل كود المشروع: من صفحة الريبو على GitHub اضغط **Code ← Download ZIP** وفك الضغط، أو لو عندك Git: `git clone` وبعدين `git checkout` للفرع المطلوب.
3. افتح Terminal (أو PowerShell على ويندوز) جوه فولدر المشروع اللي فكيته، واكتب:
   ```bash
   docker compose up --build
   ```
   أول مرة هياخد كام دقيقة (بيحمّل ويبني كل حاجة)، وبعد كده هيبقى فيه 3 حاجات شغالة: قاعدة البيانات، الـ Backend، والـ Frontend.
4. افتح المتصفح على: **http://localhost:5173**
5. بيانات الدخول التجريبية (كود الشركة `demo`، كلمة المرور واحدة لكل الحسابات `Passw0rd!123`):
   - `admin@romaerp.local` (Admin) — أو `accountant@romaerp.local` / `hr@romaerp.local` / `employee@romaerp.local`

لإيقاف كل حاجة: `Ctrl+C` في نفس الـ Terminal، وبعدين `docker compose down` لو عايز تشيل الـ containers خالص (البيانات بتفضل محفوظة في volume لحد ما تعمل `docker compose down -v`).

### 1. قاعدة البيانات

```bash
docker run -d --name romaerp-sql -e "ACCEPT_EULA=Y" -e "MSSQL_SA_PASSWORD=YourStrong@Passw0rd" -p 1433:1433 mcr.microsoft.com/mssql/server:2022-latest
```

عدّل `ConnectionStrings:Central` و`ConnectionStrings:TenantServer` في `src/RomaERP.API/appsettings.json` عند الحاجة (راجع "تعدد العملاء" تحت).

### 2. الـ Backend

```bash
dotnet tool install --global dotnet-ef
dotnet run --project src/RomaERP.API
```

عند أول تشغيل (Development) يتم تلقائيًا:
- إنشاء قاعدة بيانات مركزية (`RomaERP_Central`) وتسجيل شركة تجريبية باسم `demo` فيها.
- زرع قاعدة بيانات الشركة التجريبية (`RomaERP`): دليل الحسابات الأساسي، السنة المالية الحالية وفتراتها الشهرية، مخزن ومركز تكلفة وقسم افتراضي، وإعدادات الشركة (دولة مصر، ضريبة 14%).
- مستخدمين تجريبيين لكل دور (كلمة المرور لكل الحسابات: `Passw0rd!123`):
  - `admin@romaerp.local` (Admin)
  - `accountant@romaerp.local` (Accountant)
  - `hr@romaerp.local` (HR)
  - `employee@romaerp.local` (Employee)

الـ API متاح على `https://localhost:xxxx/swagger`. أي طلب لازم يحمل الهيدر `X-Company-Code: demo` (راجع القسم التالي).

### تفعيل المساعد الذكي (اختياري)

المساعد الذكي محتاج مفتاح API من [console.anthropic.com](https://console.anthropic.com) (منصة مطورين منفصلة عن حساب claude.ai، وليها فوترة pay-as-you-go). بعد ما تجيب المفتاح، **متحطوش في appsettings.json** — استخدم واحدة من الطرق دي:

```bash
# تطوير محلي (دوت نت user-secrets)
cd src/RomaERP.API
dotnet user-secrets set "Claude:ApiKey" "sk-ant-..."

# أو environment variable (بيشتغل في أي بيئة، فيه Docker/سيرفر إنتاج)
export Claude__ApiKey="sk-ant-..."
```

من غير مفتاح، شاشة "المساعد الذكي" بتشتغل عادي بس بترجع رسالة واضحة للمستخدم إنه لازم يتفعّل، وباقي النظام مش بيتأثر.

### 3. الـ Frontend

```bash
cd frontend
npm install
npm run dev
```

عدّل `VITE_API_URL` في `frontend/.env` إذا لزم.

## تعدد العملاء (Multi-tenancy)

كل شركة عميل ليها **قاعدة بيانات منفصلة بالكامل** — عزل تام، مفيش أي جدول مشترك بين شركتين. قاعدة بيانات واحدة صغيرة إضافية (`RomaERP_Central`) بتخزن سجل بسيط بيربط "كود الشركة" باسم قاعدة بياناتها، وهي الشيء الوحيد المشترك بين كل العملاء.

### كيف يشتغل تسجيل الدخول
كل طلب لأي endpoint (ما عدا إنشاء عملاء جدد) **لازم** يحمل هيدر `X-Company-Code` بكود الشركة (مثلاً `demo`). السيستم بيقرأ الهيدر، يدوّر على قاعدة بيانات الشركة دي، ويوجّه كل حاجة (تسجيل الدخول، الحسابات، الموظفين... إلخ) عليها تلقائيًا. الفرونت إند بيسأل عن "كود الشركة" في شاشة الدخول ويحفظه محليًا عشان يبعته مع كل طلب بعد كده.

### إنشاء عميل جديد
إنشاء شركة جديدة (قاعدة بيانات جديدة بالكامل + دليل حسابات + مستخدم Admin) بيتم عن طريق endpoint محمي بمفتاح نظام منفصل — **زي مفتاح Claude API، متحطوش في appsettings.json**:

```bash
# تطوير محلي
export System__ProvisioningKey="اختار-مفتاح-عشوائي-طويل"

curl -X POST http://localhost:5080/api/system/tenants \
  -H "Content-Type: application/json" \
  -H "X-System-Key: اختار-مفتاح-عشوائي-طويل" \
  -d '{
    "companyCode": "acme",
    "companyNameAr": "شركة أكمي",
    "companyNameEn": "Acme Co",
    "country": 2,
    "adminEmail": "admin@acme.example",
    "adminPassword": "كلمة مرور قوية",
    "taxRegistrationNumber": "123456789"
  }'
```

قيم `country`: مصر=1، السعودية=2، الإمارات=3، البحرين=4، عُمان=5، قطر=6، الكويت=7. من غير `System:ProvisioningKey` الـ endpoint بيرجع 503 (مش مفعّل) بدل ما يكون مفتوح بدون حماية.

### الضريبة (VAT) حسب الدولة
كل شركة بيتحدد لها دولة عند الإنشاء، والسيستم بيزرع تلقائيًا:
- حسابين في دليل الحسابات: **ضريبة القيمة المضافة (مدخلات)** كود `1180` أصول، و**ضريبة القيمة المضافة (مخرجات)** كود `2161` خصوم.
- نسبة الضريبة الافتراضية والعملة حسب الدولة (`CountryTaxDefaults`): مصر 14%/EGP، السعودية 15%/SAR، الإمارات 5%/AED، البحرين 10%/BHD، عُمان 5%/OMR، قطر 0% حاليًا/QAR، الكويت 0% حاليًا/KWD. القيم دي متاحة كنقطة بداية قابلة للتوسعة لدول تانية أو تحديث النسب لاحقًا.
